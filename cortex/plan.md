# 한눈 (구 CORTEX) · AI 심의위원회 계획 설계서

> 버전: v9 · 작성일: 2026-10-01
> 설계 협업: Claude · ChatGPT · Gemini (최종 판단: Claude)

---

## 1. 프로젝트 목표

**한 줄 소개**
내 자기소개서가 어떤 감정과 인상으로 읽히는지 보여주고, 채용 담당자·기술 전문가·일반 독자 AI가 토론해서 개선점을 알려주는 도구

**누구를 위한 것인가**
자기소개서를 쓰면서 여러 관점의 객관적인 피드백을 받고 싶은 IT 직군 취업 준비생

**핵심 기능 3가지**
1. 원문 위에 문장별 감정·인상을 색으로 표시하고 흐름을 보여주는 텍스트 인상 분석
2. 세 페르소나 AI의 독립 평가와 토론, 의견 변화 기록
3. 같은 글에 대한 단일 AI 피드백과 다중 AI 피드백 비교

**완성의 기준**
샘플 자기소개서 10개를 단일 AI와 다중 AI로 모두 실행하고, 결과를 블라인드로 직접 채점해 두 방식의 차이를 표로 정리

**검증하려는 질문**
서로 다른 관점을 가진 AI 에이전트들이 독립적으로 평가하고 서로의 판단을 비판·수정하면, 단일 AI보다 더 유용한 피드백이 나오는가?

## 2. 아이디어 구성

| 출처 아이디어 | 이 프로젝트에서의 역할 | 비중 |
|---|---|---|
| ① 텍스트 감정 스펙트럼 분석기 | 사용자가 처음 보는 화면. 내 글이 어떻게 읽히는지 발견하는 경험 | 약 35% |
| ② 페르소나 심의위원회 | 여러 AI의 평가·토론·종합. 프로젝트의 기술적 중심 | 약 65% |

큰 틀은 "②가 메인, ①이 분석 엔진"이며, ①은 사용자가 직접 보고 즐기는 기능으로 둔다.

**명칭**: 사용자 화면에서는 "감정·인상 분석", README·포트폴리오에서는 "텍스트 인상 및 언어적 신호 분석", 코드 내부에서는 `signals`로 부른다. 구체성처럼 감정이 아닌 특성도 포함되기 때문이다.

## 3. 설계 원칙 (합의 완료)

1. **대상 문서는 자기소개서 1종만.** 다른 문서 종류는 V2 이후.
2. **LLM은 하나만 사용.** 모델 간 비교는 V2 선택 실험.
3. **진짜 토론은 설계로 만든다.** 평가 기준 분리 + 원문 근거 기반 반박이 핵심. Temperature 조절은 보조 수단.
4. **Analyzer는 관찰만, 판단은 페르소나가.** 인상 분석 결과는 페르소나에게 먼저 주지 않는다. 페르소나는 독립 평가를 끝낸 **뒤에만**(V1) 분석 결과를 보고 반응한다.
5. **코드로 할 수 있는 건 코드로.** 문장 분리, ID 부여, 문장 길이, 숫자 포함 여부는 코드가 계산한다. LLM은 규칙화하기 어려운 판단만 맡는다.
6. **모든 근거는 코드가 검증한다.** 페르소나와 Analyzer 모두 근거를 sentence_id와 원문 인용으로 제시하고, 코드가 실제 존재 여부를 확인한다.
7. **점수는 거칠게.** 페르소나 평가는 기준별 1~5점, 문장 강도는 1~3단계. LLM의 자체 확신도(confidence)는 쓰지 않는다.
8. **인상 분석은 진단이 아니다.** "지원자가 어떤 사람인가"가 아니라 "이 글을 읽었을 때 어떤 작성자로 인식되는가"를 서술한다.
9. **동조 대비.** 토론에서 의견을 바꿀 때 원문 근거를 반드시 인용하게 하고, 근거 없는 변경은 따로 분류한다.
10. **평가의 순환논리 방지.** AI 채점은 고정 체크리스트로, 사람 채점은 블라인드로 한다.
11. **다양성은 좋다/나쁘다로 판정하지 않는다.** 세 페르소나가 같은 문제를 지적하면 중복이 아니라 중요한 합의일 수 있다.
12. **범위 확장 금지.** 새 아이디어는 V2 목록에만 적는다.

## 4. 전체 구조

```
자기소개서
   │
   ▼
[코드] 전처리: 문장·문단 분리, ID 부여(s01, p01), 길이, 숫자 포함 여부
   │
   ▼
[LLM] Analyzer (호출 1회)
   ├─ observations: 문단 역할, 기술명 포함 여부      → 페르소나에게 전달
   └─ signals: 문장별 인상 라벨, 문단별 지표 점수     → 사용자 화면에만
   │
   ├──────────────────────────────┐
   ▼                              ▼
[LLM] Persona Council (병렬 3회)   [LLM] 첫인상 생성 (호출 1회)
 서로 못 보고 독립 평가              signals를 입력으로 생성
   │                              │
   ▼                              │
[코드] 근거 검증 (validate.py)      │
   │                              │
   ▼                              │
[V1] Round 1 토론 → Shift Log       │
[V1] 분석 결과에 대한 페르소나 반응 ◄─┘
   │
   ▼
[LLM] Judge (호출 1회)
   │
   ▼
run.json  +  [V1 끝] 웹 화면
```

V0 실행 1회당 LLM 호출: Analyzer 1 + 첫인상 1 + 페르소나 3 + Judge 1 = **6회**

별도 실험 파이프라인 (V1): 같은 문서 → Single Agent / Multi-Agent → 체크리스트 평가 + 블라인드 사람 평가 → 비교

## 6. 기술 스택

- Python 3.10+ (현재 3.14) / CLI / JSON 파일 로그 / Pydantic
- LLM: **Gemini API 무료 티어** (`gemini-3.5-flash`). `utils/llm.py`로 감싸서 교체 가능. 집에서는 Ollama 로컬 모델 추가 예정
- 한국어 문장 분리: 규칙 기반 (마침표·물음표·느낌표 + 줄바꿈 문단)
- 결과 화면: 외부 라이브러리 없는 단일 HTML (`app/report.py`가 run.json으로 생성)

### 6.1 운영 제약 (V0 실행으로 확인)
- **무료 티어 하루 한도가 작다.** 모델별 하루 약 20회로 추정, 실행 1회에 6번 호출이라 하루 약 3회. 재시도도 횟수에 포함된다.
  - 대응: 호출 5초 간격·차례대로, 서버가 알려준 대기 시간 준수, 하루 한도에 걸리면 재시도 없이 즉시 중단하고 이유 표시
  - 코드·화면만 바꿨을 때는 `--mock`으로 확인하고, 실제 호출은 프롬프트 시험과 실험 데이터 수집에만 쓴다
- **한 실험 묶음 안에서는 모델을 바꾸지 않는다.** 자동 모델 전환 기능은 일부러 두지 않는다.
- (v9) **호출 안전장치**: 서버 혼잡(5xx)으로 거절된 요청도 하루 한도에 포함되는 것으로 보여 추가
  - 실행 한 번에 보내는 요청 상한 14번 (재시도 포함, `GEMINI_MAX_REQUESTS`). V1 9번 + 단일 비교 2번 + 여유 3번
  - 서버 혼잡 재시도는 단계당 2번 (`GEMINI_BUSY_RETRIES`), 30초·60초 대기. 넘으면 멈추고 "10~20분 뒤 이어서" 안내
  - 멈춰도 끝난 단계는 저장되어 같은 명령으로 이어서 실행 (AI를 다시 부르지 않음)
- 작업 장소 두 곳: 학원(내장 그래픽, 로컬 AI 비현실적) / 집(RTX 4080 Super, 로컬 AI 가능)
- 무료 티어는 입력이 학습에 쓰일 수 있으므로 **지어낸 샘플만** 넣는다.
- 실제 공개 서비스는 목표가 아니다. 공개가 필요하면 미리 돌린 결과를 결과 화면으로 보여주는 데모 방식으로 한다.

## 8. 데이터 설계

### 8.1 전처리 결과 (코드)
```json
{
  "sentences": [
    { "id": "s01", "paragraph_id": "p01", "text": "...", "length": 42, "has_number": false }
  ],
  "paragraphs": [ { "id": "p01", "sentence_ids": ["s01", "s02"] } ]
}
```
ID는 LLM이 아니라 코드가 부여한다. 모든 LLM에는 ID가 붙은 문장을 입력한다.

### 8.2 Analyzer 출력
**observations** (페르소나에게 전달)
```json
{
  "paragraph_roles": [ { "paragraph_id": "p01", "role": "도입|경험|결과|포부|기타" } ],
  "tech_mentions":   [ { "sentence_id": "s04", "terms": ["React"] } ]
}
```

**signals** (사용자 화면에만)
```json
{
  "sentence_signals": [
    {
      "sentence_id": "s03",
      "label": "자신감|망설임|방어적|열정|중립",
      "intensity": 2,
      "quote": "직접 설계했습니다",
      "reason": "자신의 역할을 단정적으로 표현함"
    }
  ],
  "paragraph_scores": [
    { "paragraph_id": "p01", "confidence": 4, "passion": 3, "tension": 2, "concreteness": 2 }
  ]
}
```
- 문장 라벨은 5개 범주 중 하나(색칠용), 강도는 1~3단계. 애매하면 `중립`.
- `quote`는 해당 문장의 실제 일부여야 하며 코드가 검증한다.
- 구체성은 감정이 아니므로 문장 라벨에서 빼고 문단 점수와 코드 관찰값(`has_number`)으로 다룬다.
- 문단 점수 4개(1~5)로 감정 흐름 곡선을 그린다. 흐름(상승/하강)은 코드가 점수에서 계산한다.

### 8.3 첫인상 (signals를 입력으로 별도 생성)
```json
{
  "archetype": "과정은 적극적으로 설명하지만 성과 앞에서는 신중해지는 설명가",
  "summary": "한 줄 요약",
  "key_contrast": "경험 문단은 확신이 강하지만 결과 문단에서 방어적 표현이 늘어남 (없으면 null)",
  "evidence_sentence_ids": ["s03", "s08"]
}
```
규칙: 성격이 아니라 "이 글에서 읽히는 작성자"를 서술한다. "열정적인 지원자" 같은 상투적 칭찬은 금지한다. 서로 다른 특징 2개를 결합한다. 대조가 실제로 없으면 억지로 만들지 않고 `key_contrast`를 null로 둔다.

### 8.4 페르소나 출력
```json
{
  "persona_id": "recruiter",
  "status": "initial",
  "scores": { "구체적 성과": 2, "직무 적합성": 4 },
  "strengths":       [{ "claim": "...", "evidence_ids": ["s03"] }],
  "weaknesses":      [{ "claim": "...", "evidence_ids": ["s07", "s08"] }],
  "recommendations": [{ "suggestion": "...", "reason": "...", "target_ids": ["s07"] }]
}
```
라운드마다 같은 스키마를 쓴다. V1의 의견 변화는 이 스키마에 필드를 추가하지 않고, 별도의 `shift_log` 레코드로 저장한다.

### 8.5 페르소나 정의 (personas.yaml)
| 페르소나 | 중점 평가 |
|---|---|
| 채용 담당자 | 구체적 성과, 직무 적합성, 차별성, 주장의 근거, 본인의 역할과 기여 |
| 기술 전문가 | 기술적 구체성, 문제→해결→결과 구조, 기술 선택의 근거, 실제 기여도 |
| 비개발 직군 면접관 (id: reader, v6에서 "일반 독자"에서 변경) | 이해 가능성, 문장 자연스러움, 흐름, 기억에 남는가 |

### 8.6 실행 로그 (run.json)
```json
{
  "run_id": "20260930_001",
  "version": "v0",
  "document": { "type": "self_introduction", "text": "..." },
```

### 8.7 근거 검증 실패 처리
잘못된 sentence_id나 원문에 없는 인용은 해당 항목만 제외하고 경고를 기록한 뒤 실행을 계속한다. 가장 비슷한 문장으로 자동 연결하지 않는다. 오류를 숨기면 "AI가 없는 근거를 만든 비율"이라는 실험 지표가 오염되기 때문이다. 제외 건수는 `invalid_evidence_count`에 기록한다.

## 9. 평가 방법

### 9.1 인상 라벨 일관성 (V0, 개발용)
- 샘플 3개 × Analyzer 5회 실행 (모든 사용자 요청을 5번 호출하지 않는다)
- 문장별 최빈 라벨 일치율, 문단 점수의 범위를 기록
- 일치율 80%를 잠정 목표로 삼되, 통과/탈락 기준이 아니라 프롬프트 개선 참고치로 쓴다
- temperature는 가능한 최저값. 단, 0이어도 완전히 같은 결과가 보장되지는 않는다
- **일관성 ≠ 정확성.** 매번 같은 라벨이 나와도 틀릴 수 있으므로, 일부 문장은 사람이 직접 라벨과 비교한다

### 9.2 Single vs Multi 체크리스트 (V1)
**Y/N 판정 항목**
| # | 항목 | 판정 |
|---|---|---|
| C1 | 모든 지적에 유효한 근거(sentence_id)가 있는가 | 코드 |
| C2 | 원문에 없는 사실이나 경험을 주장하지 않는가 | 사람 |
| C3 | 모든 약점 지적에 대응하는 수정 제안이 있는가 | 코드 |
| C4 | 수정 제안이 "보완하세요"가 아니라 구체적 행동인가 | 사람 |
| C5 | 숫자 없이 성과를 주장하는 문장(결과 문단 + has_number=false)을 지적했는가 | 코드 |
| C6 | 모호한 수식어("혁신적인", "열정적인" 등 목록)가 쓰인 문장을 지적했는가 | 코드 |
| C7 | 원문에 기술 언급이 있을 때, 그 활용 방식에 대한 피드백이 있는가 | 사람 |

**기록만 하는 지표 (좋다/나쁘다로 판정하지 않음)**
- 피드백 다양성: 서로 다른 문제 유형 수, 페르소나 간 지적 중복도
- 관점 대립: 서로 반대되는 제안이 공존하는가

### 9.3 사람 평가 (V1~V2)
Single/Multi 결과를 A/B로 섞어 블라인드로 채점한다. 샘플이 10~20개 수준이므로 통계 수치는 경향을 보여주는 참고치로만 표현한다.

### 9.4 점수 인플레이션 점검 (V0.5)
- sample_01(잘 쓴 글)의 페르소나 점수가 전부 4~5점이었다. 한 샘플만으로는 판단하지 않는다.
- **점수의 절대값보다 샘플 간 변별력을 먼저 본다.** 품질이 다른 sample_02, 03을 같은 모델·같은 프롬프트로 1회씩 돌려 분포를 비교한다. (1개 샘플 × 3회보다 3개 샘플 × 1회가 정보량이 크다)
- 비교가 끝날 때까지 **페르소나 프롬프트는 바꾸지 않는다.** 바꾸면 샘플 간 비교가 무의미해진다.
- 변별력이 없으면 "5점은 드물게" 같은 분포 조정 대신, 점수마다 **관찰 가능한 판정 기준(루브릭)**을 넣는다.
  - 예) 구체적 성과: 5 행동·결과가 명확하고 검증 가능한 수치 근거 / 4 행동·결과는 있으나 일부 정보 부족 / 3 경험은 있으나 행동이나 결과가 구체적이지 않음 / 2 경험 언급만 있고 행동·결과 거의 없음 / 1 판단할 근거 없음

### 9.5 샘플 테스트 세트 (10개)
품질이 아니라 **평가 특성**이 서로 다르게 설계한다. 모두 지어낸 글.
1. 잘 쓴 글 (sample_01) · 2. 상투적·변명조 (sample_02) · 3. 기술명 나열 (sample_03) · 4. 경험은 많지만 결과가 없음 · 5. 결과는 있지만 과정이 없음 · 6. 감정 표현이 강함 · 7. 지나치게 겸손함 · 8. 문장이 장황함 · 9. 짧고 간결함 · 10. 장점과 약점이 섞여 있음

### 9.5.1 정답지의 한계와 보완 (2026-09-30)
- 샘플과 정답지를 모두 AI(Claude)가 썼고 평가자도 AI라, AI가 정답지를 맞혀도 "AI끼리 통념이 같다"는 뜻일 수 있다 → **순환 논리 위험**
- 보완 ① 항목마다 [객관]/[주관] 표시. [객관]은 `scripts/objective_check.py` 결과를 기준으로 함 (작성자가 눈으로 센 값과 달랐던 4곳을 코드 결과로 수정함)
- 보완 ② 근거 출처 연결: STAR(UW 커리어센터), 고려대 경영대 경력개발센터 게시 칼럼, Hofstra 커리어센터, 뉴스토마토 인사담당자 감점 유형. 06(감정 과잉)·07(지나친 겸손)은 근거를 찾지 못해 [AI 판단]으로 표시
- 보완 ③ 사람 검토: 정답지를 보여주지 않는 블라인드 질문지(`review_sheet.md`)로 1~3명에게 의견을 받고, [AI 판단] 항목은 사람 답과 겹칠 때만 보고서 근거로 쓴다
- 보고서에 이 한계를 반드시 명시한다

### 9.6 결과 화면 구성 (2026-09-30 오후, 사용자 피드백으로 4차 재설계)
피드백 흐름: "보고서 같다" → 대화형 → "채팅 뒤 대시보드처럼" → "가독성이 떨어지고 흐름을 모르겠다" → **한 장씩 넘겨 읽기** → "마지막에 요약"
한 페이지(`demo/index.html`, 템플릿 `app/screens/app.html`) 안에서 세 단계로 넘어간다.
1. **글 넣기**: 입력칸 + 샘플 10개(결과 있음/준비 중). 공개 사이트는 미리 돌려 둔 샘플만, 로컬(`python -m app.server`)은 실제 분석
2. **심의 중 (채팅 연출, 10~15초)**: 의장 시작 → 분석가 첫인상 → 평가자 3명 총평 + 아쉬운 점 1개 → 의장이 갈린 판정을 짚고 결과로 넘김. 로컬 실제 분석 중에는 실제 진행 단계를 표시
   - V0의 평가자들은 서로 보지 않았으므로 대화는 **연출**이다. 화면에 명시한다 (9.6.1)
3. **결과 8장** (V1은 토론 장을 더해 9장): 첫인상 → 채용 담당자 → 기술 전문가 → 비개발 직군 면접관 → (토론) → 갈린 판정 → 고칠 것 → 원문 → 요약
   - 한 장에 한 가지 이야기, 제목은 그 장의 결론 문장. 다음 버튼에 다음 장 이름, 위쪽 목차 막대, 키보드 ←→·옆으로 밀기
   - 평가자 장: 좋았던 점 1 / 아쉬운 점 1(근거 문장) / 고쳐보면 1 / 기준별 점수, 나머지는 접기. 평균 점수는 표시하지 않음 (거짓 정밀도)
   - 갈린 판정은 의장 요약이 아니라 코드가 근거 데이터에서 계산 (한 명은 강점, 다른 한 명은 아쉬움으로 인용한 문장)
   - 문장 번호를 누르면 원문 장으로 이동해 그 문장의 인상·판정을 보여줌
- 색: 자신감·열정·망설임 3색 + 방어적 빗금 + 중립 무색 (4색은 색각 검증 실패). 사이트 "행로" 스타일 유지
- `--mock` 결과는 데모에 넣지 않는다

#### 9.6.1 화면 검토 반영 (인수인계 v7, ChatGPT·Gemini)

- 채팅 시작에 "실제 토론이 아니라 각자 쓴 평가를 순서대로 보여주는 연출"이라고 명시 (ChatGPT 안. Gemini는 현재로 충분하다고 했으나 오해 비용이 더 크다고 판단)
- 첫 화면 입력칸 근처에 "공개 데모는 미리 분석한 샘플만, 이유(무료 한도·개인정보)" 명시 (두 AI 동의)

#### 9.6.2 화면용 짧은 글: 편집자 단계 (인수인계 v8, 2026-09-30)
- 진단: 화면을 여러 번 바꿔도 "읽히지 않는다"는 반응이 반복된 원인은 디자인이 아니라 **AI 평가 원문의 보고서 말투와 길이**. 손으로 줄인 시안에 사용자 반응이 좋아서 확인 (두 AI 동의)
- 편집자: 평가가 끝난 뒤 화면용 글만 쓰는 **별도 AI 호출** (`app/editor.py`, `prompts/editor.txt`). 평가 프롬프트에 섞지 않음 (평가와 표현이 섞이면 실험 데이터가 흔들림, 두 AI 동의)
  - 규칙: 판정·강도 변경 금지("다소 부족"→"없다" 금지, ChatGPT), 새 사실·예시 금지, 숫자·고유명사 유지, 담백한 해요체 (두 AI 동의)
  - 코드 검증: ref 1:1 대응, 글자 수(제목 32자·설명 70자) 초과 시 원문으로, 원문의 숫자·영문 고유명사가 모두 빠지면 경고 기록 (Gemini 안)
  - 사람 검증: 샘플 몇 개를 원문과 대조 (ChatGPT 안). 모든 카드에 "원래 평가" 펼치기
  - 저장: run.json의 `display`에만. 채점·실험에는 영향 없음. 가짜 응답(mock)은 실제 결과에 쓰지 않음
  - 비용: 평가 실행(6번)과 분리해 `python -m app.editor`로 따로 실행 (결과 1개당 1번). 로컬 서버에서는 분석 직후 자동 실행. 화면용이라 평가와 다른 모델(로컬 AI)을 써도 원칙 위반이 아님
- 결과 화면: 짧은 글 카드형 (평가자 장마다 좋았던 점·아쉬운 점·고쳐보면 1개씩 + 더 보기, 한 장이 한 화면)

#### 9.6.3 디자인 마무리 (2026-10-01, 인수인계 v10·v11)
원칙: 그림은 **정보 전달을 돕는 곳에만**, 결과·근거·점수는 기존 화면이 담당한다. "예쁘게 꾸미기"가 아니라 의미 전달·여백 보완·빈 상태 처리가 목적.

- **캐릭터와 그림 (사용자 제작)**: 분석가·채용 담당자·기술 전문가·비개발 직군 면접관·의장 5명
  - 첫 화면 히어로(세 사람이 한 종이를 읽는 그림). 캐릭터 소개는 ① 첫인상(분석가) / ② 평가자 3명 / ③ 정리(의장)로 묶음 → "5명이 평가하나?" 오해 방지 (ChatGPT)
  - 토론 장 상단 그림(V1), 첫인상 장 아래 분석가 메모 그림("그림 속 메모는 예시예요" 표시, 실제 결과로 오해되지 않게), 요약 끝 마무리 그림, 의장 고민 그림(준비 중·분석 오류·빈 결과 안내에 공통)
  - 그림 바탕은 종이색에 맞추고 밝은 모드는 가장자리를 녹이고, 다크 모드는 둥근 종이 카드로
- **표정 세트** (평가자마다 6가지, `demo/assets/face/`): 표정이 뜻을 가질 때만 바꿈
  - 갈린 판정: 강점 → 긍정, 아쉬움 → 고민·의문, 둘 다 → 고민
  - 심의 채팅: 읽는 중 → 일하는 표정, 평가 점수 평균 4 이상 → 긍정 / 2.5 이하 → 아쉬움, 의장은 판정이 갈릴 때 고민 · 정리할 때 확신
  - 토론: 유지 → 확신, 근거 있는 변경 → 놀람(새로 알게 됨), 근거 없는 변경 → 고민
  - 평가자 장 맨 위는 대표 초상 유지 (누구 장인지 먼저 알아보게)
- **판정 표시**: ✓ ± △ 기호만으로는 뜻이 바로 읽히지 않음 (사용자 지적) → **아이콘 + 글자** ("강점 / 아쉬움 / 강점+아쉬움"), 고칠 것은 연필 아이콘. 심의 표는 칸이 좁아 아이콘만 두고 표 위에 범례
- **기능 보완**
  - 고칠 것 장: 의장이 꼽은 문제마다 그 문제를 낸 평가자의 같은 문장 제안을 붙여 **"이렇게 고쳐보면"** 표시 (문제만 있고 방법이 없던 문제 해결)
  - "이렇게 고쳐보면"마다 **복사 버튼** (짧은 글이 아니라 원래 상세 제안을 복사) (Gemini)
  - 밝게/어둡게 전환 버튼 (처음엔 기기 설정, 누르면 기억). 상단 로고 확대 · 여백, "← 행로" 제거 → 맨 아래 작은 포트폴리오 링크
  - 요약 끝: 그림 + "심의가 끝났어요" + 버튼을 한 카드로 묶음. 버튼 이름을 목적지가 보이게("결과 처음부터 보기 / 심의 과정 다시 보기") (ChatGPT)
  - 샘플 카드: 마우스를 올린 모양과 선택한 모양이 비슷해 "두 개 선택됨"으로 보이던 문제 수정 ("선택함" 표시) (ChatGPT)
  - 링크 미리보기 이미지(1200×630)와 설명 (카톡 등 공유용)
  - 어조 색을 그림 팔레트에 맞춰 차분하게 (자신감 #3d6fa3 · 열정 #d4703f · 망설임 #3f9580)
- **채택하지 않은 것**: 이모지 우선순위 표시(이미 높음·중간·낮음 표시가 있고 분위기와 안 맞음), 결과 장마다 그림 추가(앱이 가벼워 보임, ChatGPT도 같은 의견), 분석 중·완료·오류 아이콘과 소품 스티커(들어갈 자리 없음). 공통점·차이점 아이콘은 단일 AI 비교 화면에서 사용 예정
- **검토 과정의 실수**: 인수인계 v10 사진을 편집자 짧은 글이 없는 예전 결과로 찍어서, 두 AI 모두 "채팅이 너무 길다"를 1순위로 지적함. 실제 결과로 다시 확인하니 이미 짧게 나오고 있었음 → 이후 사진은 항상 사용자 PC의 최신 결과로 찍는다

#### 9.6.4 첫 화면 재배치 (v9, 사용자 피드백 "세로로 너무 길고 좌우 여백이 많다")

## 13. V1 설계 (2026-09-30, 세 AI 검토 반영)

### 13.1 목표
"토론이 판단을 바꾸는가"와 "여러 관점이 단일 AI보다 나은가"를 **같은 샘플·같은 모델**로 측정할 수 있게 만든다.

### 13.2 Multi 흐름 (실행 1회 LLM 호출 9번)
```
전처리 → Analyzer(1) → 첫인상(1)
      → Round 0: 페르소나 3명 독립 평가(3)        ← V0와 동일
      → Round 1: 페르소나 3명 토론(3)            ← 새로 추가
      → [코드] Shift Log 계산
      → Judge(1): Round 1 결과 + Shift Log를 보고 종합
```

### 13.3 Round 1 (토론) 입력과 규칙
- 입력: 원문(문장 ID) + 관찰 사실 + **자기 Round 0 결과** + **다른 두 평가자의 Round 0 결과**
- 다른 평가자는 **익명(평가자 A·B) + 그 평가자의 평가 기준 목록**으로 보여준다 (13.10-1)
  - 매핑(A=누구, B=누구)은 run.json에 기록하고 결과 화면에서는 역할 이름으로 공개
- 세 명이 **동시에** 답한다: 모두 다른 사람의 Round 0만 보고, 서로의 Round 1은 보지 않음 → 순서 효과가 구조적으로 없음 (13.10-4)
- 인상 신호(signals)는 여전히 주지 않는다 (원칙 4). 페르소나 반응은 V1 후반에 따로 검토
- 해야 할 일
  1. 다른 평가자의 지적 중 자기 기준으로 **동의 / 반대 / 부분 동의**를 밝힌다 (근거 문장 ID 필수)
  2. 자기 Round 0 결과를 **유지하거나 고친다**. 점수도 바꿀 수 있다. 바꿀 때는 무엇이 왜 바뀌었는지와 원문 근거를, **유지할 때도 반대 의견을 보고도 유지한 이유**를 쓴다 (13.10-5)
  3. 다른 평가자 덕분에 **새로 발견한 점**이 있으면 추가한다 (자기 기준 안에서만)
- 금지: 근거 없이 다른 평가자 의견을 따라가기, 자기 평가 기준 밖의 판단 대신하기
- 프롬프트는 **중립**으로 쓴다: "원문 근거가 뒷받침할 때만 바꾸고, 유지도 똑같이 정당한 선택"까지만. "쉽게 철회하지 말라" 같은 방어 지시는 넣지 않는다 (유지 쪽으로 결과를 미리 기울이므로 측정이 오염됨, 13.10-6)
- 출력: Round 0와 **같은 스키마**(최종 입장) + `responses`(다른 평가자 지적에 대한 동의/반대 목록) + `changes`(스스로 밝힌 변경 이유)

### 13.4 Shift Log (코드가 계산 + AI 자기 보고 대조)
- 평가자마다 Round 0 → Round 1을 비교: 기준별 점수 변화, 약점 문장 추가·삭제, 강점 문장 추가·삭제. **점수 변화와 지적 변화는 따로 기록**한다 (Gemini 안)
- 분류 (앞서 합의한 3종)
  - `maintained`: 점수·지적 변화 없음
  - `changed_with_valid_evidence`: 변화가 있고, `changes`에 **원문에 실제로 있는** 문장 ID와 이유가 있음
    - 코드가 확인하는 것은 "근거 문장이 존재한다"까지다. "그 근거가 변경을 정말 뒷받침한다"는 뜻이 아니다 (13.10-3). 보고서에서도 이렇게 구분해 쓴다
    - 뒷받침 여부는 사람이 일부 사례만 직접 확인한다 (AI로 자동 판정하지 않음: 순환 논리)
  - `changed_without_evidence`: 변화가 있는데 근거가 없거나 검증 실패 → **동조 의심**
- 추가 기록: `adopted_from` — 새로 생긴 약점 문장이 다른 평가자의 Round 0 약점과 같으면 누구에게서 왔는지 기록 (동조 흐름 추적)
- AI의 자기 보고(`changes`)와 코드가 계산한 실제 변화가 다르면 불일치로 기록한다 (말로는 유지했다면서 실제로 바뀐 경우 등)

### 13.5 Single 비교 기준
- **Single-A (주 비교)**: 단일 AI 1회. 입력은 Multi와 같은 원문 + 관찰 사실. **세 평가자의 기준 13개를 모두 준다.** 출력은 페르소나와 같은 스키마
  - 이유: 기준을 다 주지 않으면 "여러 관점의 효과"가 아니라 "기준 개수의 효과"를 재게 된다
- 해석 범위 (ChatGPT 안): "Multi가 우수했다"가 아니라 "같은 13개 관점을 한 번에 평가한 경우와, 세 독립 평가를 종합한 경우에 어떤 차이가 관찰됐는가"로 쓴다. 에이전트 수·독립 추론의 효과가 섞여 있기 때문
- Single-B (보조, 선택): "이 자기소개서를 평가하고 개선점을 알려줘" 수준의 단순 프롬프트. 실제 사용자가 AI에 그냥 물어보는 상황의 기준선
- 결과는 run.json의 `single`에 저장하고 `scripts/grade.py`가 같은 방식으로 채점 (이미 대비됨)

### 13.6 호출 예산
| 방식 | 샘플 1개 | 샘플 10개 |
|---|---|---|
| Multi (V1) | 9 | 90 |
| Single-A | 1 | 10 |
| Single-B | 1 | 10 |
| 합계 | 11 | 110 |
- Gemini 무료(하루 약 20회 추정)로는 약 6일, 집의 로컬 AI로는 하루 안에 가능
- 공정성: 방식별 호출 수와 토큰 수도 함께 보고한다 (Multi가 계산을 더 많이 쓰는 것은 사실이므로)
- (v9) **실행 계획 확정 (최소 호출 경로)**: 중간 점검 2차 목표는 "비교할 수 있는 상태"이므로 성격이 다른 **샘플 3개**로 먼저 완성
  - 샘플 01(잘 쓴 글) · 02(상투어·변명조) · 03(기술만 나열)
  - 샘플마다 한 줄로: `python -m app.main --file … --v1 --single ab` (11번). 따로 돌리면 분석가 단계를 다시 부르므로 함께 실행
  - 하루 2개 이하: 1일차 01 + 02 시작(한도에서 저장된 채 멈춤) → 2일차 02 이어서 + 03
  - 호출을 쓰지 않는 단계는 언제든: 편집자(`gemini-3.5-flash-lite`, 한도 별도), 채점, 화면 생성
  - 하지 않는 것: V0 재실행, 같은 샘플 반복, 비교 장 전에 샘플 늘리기, 묶음 중간 모델 변경
  - 나머지 7개는 Gemini로 이어 가거나, 집의 로컬 AI로 **별도 묶음**으로 실행해 따로 보고

### 13.8 결과 화면 추가 (V1 끝)
- 결과 장에 "토론 뒤 어떻게 바뀌었나" 추가: 평가자마다 Round 0 → 다른 사람 주장 → 응답 → 근거 → Round 1 (ChatGPT: 점수 변화가 아니라 판단 변화의 과정이 핵심 데이터)
- Shift Log 요약: 유지 / 유효한 근거로 변경 / 근거 없이 변경 수
- 채팅 연출 문구를 "각자 평가 → 토론"으로 바꾼다 (이때부터는 실제 토론)
- (v8) 구현 완료. 실제 V1 결과로 다시 점검할 것: 토론 글이 길면 응답 카드 줄이기
- (v8) **단일 AI 비교 장**: 원문 장과 요약 장 사이에 새 장으로 (ChatGPT). 점수 우열이 아니라 **"어떤 문장을 발견했는가"**를 보여줌: 공통 발견 / 한눈만 발견 / 단일 AI만 발견 + 문장 번호. 공통점·차이점 아이콘 사용

### 13.9 검토 결과 요약 (인수인계 v7)
| 쟁점 | ChatGPT | Gemini | 결정 |
|---|---|---|---|
| 1. 역할 이름 vs 익명 | 익명, 화면에서 공개 | 역할 이름 (관점 맥락 필요) | **익명 + 평가 기준 목록 제공** |
| 2. Single-A 13기준 | 쓸 만하나 해석 제한 | 가장 공정 | **유지 + 해석 범위 제한** |
| 3. 코드만으로 근거 판정 | 불충분 | 1차 필터로 충분 | **`changed_with_valid_evidence`로 이름 변경, 뒷받침 여부는 사람이 일부 확인** |
| 4. 순서 | 차례로 + 순서 돌리기 | 동시 | **동시** |
| 5. 점수 변경 | 허용 + 변경·유지 이유 | 허용 + 점수·지적 분리 기록 | **둘 다 채택** |
| 6. 가장 큰 구멍 | AI 정답지로 AI 채점 (순환) | 동조로 인한 다양성 소멸 | **둘 다 리스크로 등록 (10장)** |

### 13.10 결정 이유
1. **익명 + 기준 목록**: 역할 이름("기술 전문가")은 권위 효과를 줄 수 있고(ChatGPT), 완전 익명은 관점 맥락을 잃는다(Gemini). 이름 대신 "평가자 A — 보는 기준: 이해 가능성, 문장 자연스러움, 흐름, 기억에 남는가"를 주면 맥락은 주고 직함 권위는 뺄 수 있다. 한계: 글투나 용어로 역할을 짐작할 수는 있다
2. **Single-A 해석 제한**: 13.5 참고
3. **근거 판정**: Gemini 말대로 코드 검증은 "없는 근거를 지어내며 입장을 바꾸는" 동조를 걸러내는 1차 필터로 유효하다. 하지만 유효한 문장 번호를 댔다고 설득이 타당한 것은 아니므로(ChatGPT), 이름과 해석을 좁힌다
4. **동시 응답**: 차례로 하면 순서 효과가 생기고, 샘플 10개로 순서를 돌려도 통제가 어렵다(ChatGPT도 인정). 동시에 하면 처음부터 생기지 않는다. 순서 효과 자체는 나중에 별도 실험
5. **점수 변경 허용**: 지적을 받아들였다면 점수도 바뀌는 것이 자연스럽다(Gemini). 유지 이유까지 받아야 "안 바뀐 것"도 데이터가 된다(ChatGPT). 많이 바뀌었다고 좋은 것도, 안 바뀌었다고 나쁜 것도 아니다
6. **방어 프롬프트 불채택**: Gemini가 제안한 "쉽게 철회하지 말라"는 동조를 막지만, 반대로 고집을 만들어 "유지"가 늘어난 결과가 프롬프트 탓인지 판단 탓인지 구분할 수 없게 된다. 중립 지시로 두고 동조가 실제로 얼마나 일어나는지를 **측정**하는 것이 이 실험의 목적이다
- 인용 확인: Gemini가 든 "Sycophancy in Language Models"의 실제 제목은 "Towards Understanding Sycophancy in Language Models" (Sharma 외, Anthropic, 2023). 내용(모델이 상대 의견에 맞추는 경향)은 맞음

### 13.11 보고서 원칙 (인수인계 v12, ChatGPT·Gemini 검토 반영)
두 AI 모두 "디자인은 마무리하고 실험으로 넘어갈 것"으로 답함. 보고서에 지킬 것:
1. **비교 조건 표**: 한눈 / Single-A / Single-B의 입력(원문·문장 번호)·평가 기준·호출 수를 표로 적는다. Single-A는 같은 기준 13개를 한 번에, Single-B는 일부러 기준 없는 단순 프롬프트 → "조건이 다른 비교군"으로 명시 (ChatGPT)
2. **발견을 숫자로**: 공통 발견 / 한눈만 / 단일만의 문장 개수와 문장 번호, 근거가 실제 원문과 맞는지를 표로. **단일 AI만 찾은 것도 똑같이 보여준다** (점수 우열 비교 금지, 두 AI 동의)
3. **동조 용어 제한**: "근거 없는 변경"은 바꾼 이유에 원문 문장을 대지 않았다는 뜻일 뿐이므로 비율로만 보고. 다른 평가자의 첫 평가 지적을 그대로 따라간 흔적(`adopted_from`)이 있는 경우만 "동조로 의심되는 사례"로 따로 센다 (Gemini의 "근거 없는 변경 = sycophancy" 정의는 과장이라 채택하지 않음)
4. **결론 범위**: "입증"이 아니라 "이번 실험에서 관찰된 차이". 샘플 3개·사람 검토 1~3명 규모와 AI가 만든 정답지의 한계(자동 채점은 참고 지표)를 한계 절에 적는다 (두 AI 동의)
