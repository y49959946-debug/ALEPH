프로젝트 개요

가상의 메모 자료실 웹사이트를 혼자 운영하며, 단계가 올라갈 때마다 새로운 방식의 공격을 막아 내는 과제입니다. 취약점 분석부터 코드 수정, 커밋·배포, 단계별 결과 제출까지 직접 했고, 단계마다 한 일과 막힌 점을 기록해 제출했습니다.

“추측으로 고치지 않고, 로그와 실행 결과로 원인을 확인한 뒤 고칩니다.”

방어전에서 지킨 원칙

숫자로 보기

완주22단계1~5단계 만점, 보너스 과제 2개도 해결했습니다.
8단계14번 재시도가설을 하나씩 좁혀 가며 끝내 통과했습니다.
10단계11번 재시도반복된 실패를 공부할 기회로 삼았습니다.

단계별 기록

각 단계를 눌러 상황, 한 일, 결과를 볼 수 있어요. 심판 시스템이 거부한 코드와, 그 뒤에 원인을 찾아 고친 과정도 함께 적었습니다.

1단계출발점 확인로그인 없이 가상 메모 4건이 공개된 상태를 확인
상황
공격자에게 점령된 가상 메모 자료실을 직접 배포하고, 어떤 자료가 밖으로 드러나 있는지 확인해야 했습니다.
한 일
과제의 Deploy 버튼으로 내 계정에 GitHub 저장소와 Vercel 배포를 만들었습니다. 로그인하지 않은 상태로 /data.json을 열어, 가상 메모 4건이 그대로 공개돼 있다는 걸 확인했습니다.
결과
배포 주소를 제출해 1단계를 마쳤고, 이후 단계에서 막아야 할 출발점을 확인했습니다.
2단계자료를 DB로 옮기고 공개 파일 없애기Supabase + RLS, 심판 거부 S02_MARKER_IN_STATIC 해결
상황
메모 자료가 코드와 정적 파일(data.json)에 그대로 들어 있어, 주소만 알면 누구나 메모 4건을 볼 수 있었습니다.
한 일
메모를 Supabase notes 테이블로 옮기고 RLS를 켜서 공개 읽기를 막았습니다. 화면은 서버 함수(/api/notes)로 메모를 받아 오게 바꾸고, DB 키는 Vercel 환경변수에만 두었습니다. 모든 응답에 보안 헤더(X-Content-Type-Options: nosniff)를 붙였습니다. 처음엔 data.json의 메모만 비웠다가 심판이 S02_MARKER_IN_STATIC으로 거부해, 저장소와 빌드 결과에서 파일을 모두 지우도록 빌드 스크립트를 고쳤습니다.
결과
/data.json이 404가 되어 정적 파일로 자료가 새던 길이 사라졌습니다.
3단계로그인한 사람에게만 자료 주기요청마다 로그인 토큰 검사
상황
DB 키는 숨겼지만 메모를 주는 서버 함수에 로그인 확인이 없어, 주소만 알면 누구나 메모를 받아 갈 수 있었습니다.
한 일
Supabase 이메일 로그인·로그아웃 화면을 만들고, 자료 API가 요청마다 로그인 토큰을 검사해 확인되지 않으면 자료를 주지 않게 했습니다. 토큰과 키 같은 비밀 값은 코드·Git·화면에 남기지 않았습니다.
결과
로그인하지 않은 요청은 메모를 받을 수 없게 됐습니다. 다만 누구의 메모인지는 아직 구분하지 않았고, 4단계에서 막았습니다.
4단계내 메모만 다룰 수 있게서버 소유자 검사 + DB RLS, 두 겹 방어
상황
로그인만 하면 다른 사람의 메모까지 읽고 고칠 수 있는 상태였습니다.
한 일
메모 API가 요청한 사용자와 메모의 소유자(owner_id)를 대조해 내 메모가 아니면 거부하게 했습니다. 서버 코드에만 의존하지 않도록 DB에도 RLS 정책과 최소 권한 SQL을 적용했습니다.
결과
로그인한 사용자도 다른 사람의 메모에는 접근할 수 없게 됐고, 검사를 서버 API와 DB 두 겹으로 적용했습니다.
5단계DB 원본 직접 접근 막기권한 회수 SQL, 심판 거부 S05_ORIGINAL_URL_MISSING 해결
상황
우리 API를 거치지 않고 DB 원본 주소로 직접 접근하는 길이 남아 있었고, 로그인 화면에 DB 공개 키가 들어 있었습니다.
한 일
DB 원본 직접 접근 권한을 회수하는 SQL을 적용하고, 로그인도 서버 함수(api/auth.js)를 거치게 바꿔 화면 파일에서 공개 키를 없앴습니다. 심판이 S05_ORIGINAL_URL_MISSING으로 거부해, 빌드 스크립트가 원본 주소 값을 채우도록 고쳐 다시 제출했습니다.
결과
이제 자료는 우리 서버 함수를 통해서만 오갑니다.
6단계등록된 기기만 들여보내기제로 트러스트: device_registered 규칙
상황
계정만 맞으면 어떤 기기에서든 자료실에 들어올 수 있었습니다.
한 일
판정기(src/decider.mjs)에 등록 기기 규칙을 더해, 등록된 기기일 때만 읽기를 허용하고 아니면 device_not_registered로 거부했습니다. 브라우저가 보낸 사용자 번호나 역할처럼 조작될 수 있는 값은 판정에 쓰지 않았습니다.
결과
시험에서 등록 기기는 허용, 미등록 기기는 거부로 판정됐고, 기존 로그인·메모 기능은 그대로 유지했습니다.
7단계이상 접속일 때만 다시 로그인새벽 + 처음 보는 네트워크 + 대량 요청이 겹칠 때 step-up
상황
등록된 기기라도 평소와 다른 의심스러운 접속이 그대로 통과되고 있었습니다.
한 일
새벽(0~5시), 처음 보는 네트워크, 최근 10분 10건 이상 요청이 모두 겹칠 때만 다시 로그인(step_up_required)을 요구하게 했습니다. 지역 하나만으로는 차단하지 않아 정상 사용자가 막히지 않게 했고, 다시 로그인은 300초 안일 때만 인정했습니다.
결과
가상 시험 4항목이 통과했습니다. 실제 재로그인 흐름은 값을 채워 줄 엔진이 없어 실측하지 못했고, 그 사실을 README에 그대로 적었습니다.
8단계구역별 접근 통제심판 거부 S08_OTHER_ZONE_ALLOWED, 14번 재시도 끝에 통과
상황
내 메모·반 공지·강사 자료가 같은 규칙으로 열려 있어, 한 구역의 권한으로 다른 구역에 넘어가거나 여러 사람의 메모를 한꺼번에 가져갈 수 있었습니다.
한 일
자원을 세 구역으로 나누고, 메모는 한 건씩만 다루게 하며 전체 목록 조회(GET /notes)는 거부했습니다. 공지와 강사 자료는 읽기만 허용했습니다. 심판이 S08_OTHER_ZONE_ALLOWED로 거부한 뒤에는 추측으로 한꺼번에 고치지 않고, 가설을 하나씩 좁혀 가며 저장점을 13번 만들었습니다. 원인은 메모 전체 목록을 돌려주는 경로였습니다.
결과
다른 사용자(B)가 A의 메모 주소를 직접 부르면 403(OWNER_MISMATCH)으로 막히는 구조가 됐고, 8단계를 통과했습니다.

9~12단계에서는 예전 모의해킹 실습에서 사이트를 직접 만들어 본 경험이 12단계를 푸는 데 도움이 됐습니다. 13~22단계는 직접 만든 보안 에이전트로 통과했고, 그 과정은 제로트러스트·XDR 보안 서비스에 정리했습니다.

막혔던 순간과 배운 점

상황
8단계와 10단계에서 같은 공격을 몇 번이고 막지 못했고, 같은 점검을 매번 손으로 반복하고 있었습니다.
행동
실패하면 지금 무엇을 하고 있는지부터 파악하고, 커밋마다 무엇을 바꿨는지 기록해 같은 시도를 되풀이하지 않았습니다. 반복하던 점검 과정은 공격 흔적을 로그에서 찾아 원인과 수정 방향을 정리하는 보안 에이전트로 만들었습니다.
배운 점
눈에 띄는 경로만 막아서는 부족하고, 데이터가 빠져나갈 수 있는 모든 길을 확인해야 한다는 것을 배웠습니다. 문제를 하나씩 막는 데서 그치지 않고, 같은 문제를 다시 겪지 않도록 방식 자체를 바꾸는 것이 제가 일하는 방식입니다.

이어진 작업: Veil 0.1.0 배포

방어전을 토대로 만든 보안 에이전트를 PC에서 쓰는 관제 대시보드 앱 Veil로 완성했습니다. 상단 상태 카드 4개와 추이·기록을 한 화면에서 보는 구성이며, 설치 프로그램으로 포장해 배포했습니다.
